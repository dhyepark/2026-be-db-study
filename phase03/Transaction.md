# 5. 트랜잭션과 락

## 5.1 트랜잭션

### 5.1.1 MySQL에서의 트랜잭션

트랜잭션은 하나의 논리적인 작업 셋에 하나의 쿼리가 있든 두 개 이상의 쿼리가 있든 관계없이 논리적인 작업 셋 자체가 100% 
적용되거나 아무것도 적용되지 않아야 함을 보장해 주는 것이다.


### 5.1.2 주의 사항

트랜잭션 또한 DBMS의 커넥션과 동일하게 꼭 필요한 최소의 코드에만 적용하는 것이 좋다. 
이는 프로그램 코드에서 트랜잭션의 범위를 최소화 하라는 의미다.

다음 내용은 사용자가 게시판에 게시물을 작성한 후 
저장 버튼을 클릭했을 때 서버에서 처리하는 내용을 순서대로 정리한 것이다.

```text

1) 처리 시작
==> 데이터베이스 커넥션 생성
==> 트랜잭션 시작

2) 사용자의 로그인 여부 확인
3) 첨부로 업로드된 파일 확인 및 저장
...
6) 첨부 파일 정보를 DBMS에 저장
...
8) 게시물 등록에 대한 알림 메일 발송
9) 알림 메일 발송 이력을 DBMS에 저장
<== 트랜잭션 종료(COMMIT)
<== 데이터베이스 커넥션 반납

10) 처리 완료
```

위의 단계에서 문제가 되는 단계는 8번이다.
메일 전송이나 FTP 파일 전송 작업 같은 작업은 어떻게 해서든 DBMS의 트랜잭션 내에서 제거하는 것이 좋다.
이유는 프로그램이 실행되는 동안 메일 서버와 통신할 수 없는 상황이 발생한다면, 웹 서버뿐 아니라 DBMS 서버까지 위험해지는 상황이 발생할 것이기 때문이다.

## 5.2 MySQL 엔진의 락

MySQL에서 사용되는 락은 크게 스토리지 엔진 레벨과 MySQL 엔진 레벨로 나눌 수 있다.

MySQL 엔진은 MySQL 서버에서 스토리지 엔진을 제외한 나머지 부분으로 이해하면 되는데, 
MySQL 레벨의 잠금은 모든 스토리지 엔진에 영향을 미치지만, 스토리지 엔진 레벨의 잠금은 스토리지 엔진 간 상호 영향을 미치지 않는다.

### 5.2.1 글로벌 락

글로벌 락(GLOBAL LOCK)은 `FLUSH TABLES WITH READ LOCK` 명령으로 획득할 수 있으며, MySQL에서 제공하는 잠금 가운데 가장 범위가 크다.

한 세션에서 글로벌 락을 획득하면 다른 세션에서 SELECT를 제외한 대부분의 DDL 문장이나 DML 문장을 실행하는 경우 글로벌 락이 해제될 때까지 해당 문장이 대기상태로 남는다.

글로벌 락이 영향을 미치는 범위는 MySQL 서버 전체이며, 작업 대상 테이블이나 데이터베이스가 다르더라도 동일하게 영향을 미친다.

---

### 5.2.2 테이블 락

테이블 락(Table Lock)은 개별 테이블 단위로 설정되는 잠금이며, 명시적 또는 묵시적으로 획득할 수 있다.

명시적인 테이블 락은 `LOCK TABLES` 명령으로 획득하며 `UNLOCK TABLES` 명령으로 해제할 수 있다.

```sql
LOCK TABLES table_name READ;
LOCK TABLES table_name WRITE;

UNLOCK TABLES;
```

명시적인 테이블 락은 온라인 서비스에 미치는 영향이 크기 때문에 특별한 경우가 아니라면 애플리케이션에서 사용할 필요가 거의 없다.

묵시적인 테이블 락은 MySQL이 자동으로 획득하는 잠금이다.

MyISAM이나 MEMORY 스토리지 엔진에서는 데이터를 변경하는 쿼리가 실행되면 자동으로 테이블 전체에 잠금을 설정하고, 쿼리가 종료되면 즉시 해제한다.

반면 InnoDB는 레코드 기반 잠금을 사용하므로 일반적인 DML에서는 테이블 락 대신 레코드 락을 사용한다. 다만 DDL을 수행하는 경우에는 테이블 락의 영향을 받는다.

---

### 5.2.3 네임드 락

네임드 락(Named Lock)은 테이블이나 레코드가 아닌 사용자가 지정한 문자열(String)에 대해 설정하는 잠금이다.

`GET_LOCK()` 함수를 이용해 획득하며, `RELEASE_LOCK()` 함수로 해제할 수 있다.

```sql
SELECT GET_LOCK('mylock', 2);

SELECT IS_FREE_LOCK('mylock');

SELECT RELEASE_LOCK('mylock');
```

여기서 중요한 점은 네임드 락이 실제 데이터에 직접 걸리는 락은 아니라는 점이다.

레코드 락은 특정 row를 잠그기 때문에 다른 트랜잭션이 같은 row를 변경하려고 하면 DB가 직접 막아준다. 반면 네임드 락은 사용자가 정한 문자열 이름에만 락을 거는 방식이다.

예를 들어 아래 쿼리를 실행했다고 해서 `coupon` 테이블의 `id = 1` row가 자동으로 잠기는 것은 아니다.

```sql
SELECT GET_LOCK('coupon:1', 3);
```

다른 코드가 네임드 락을 사용하지 않고 바로 `UPDATE coupon ...`을 실행하면 MySQL은 이를 네임드 락 때문에 막지 않는다.

즉 네임드 락은 데이터 자체를 보호하는 락이라기보다, 애플리케이션에서 정한 작업 단위가 동시에 실행되지 않도록 막는 보조적인 동시성 제어 수단에 가깝다.

네임드 락의 이름은 회사나 서비스에서 정하는 컨벤션이다. MySQL은 문자열의 의미를 알지 못하고, 같은 문자열인지 아닌지만 판단한다.

```sql
SELECT GET_LOCK('issue-coupon:user:1:coupon:100', 3);
```

위 문자열은 `1번 사용자가 100번 쿠폰을 발급받는 작업`이라는 의미로 애플리케이션에서 약속한 이름일 뿐이다. 같은 작업인데 어떤 코드는 `issue-coupon:user:1:coupon:100`을 사용하고, 다른 코드는 `coupon:100:user:1`을 사용하면 MySQL은 서로 다른 락으로 판단한다.

따라서 네임드 락을 사용할 때는 락 이름을 만드는 규칙을 일관되게 유지해야 한다.

네임드 락은 다음과 같은 상황에서 사용할 수 있다.

- 아직 잠글 row가 없을 때: 사용자별 하루 출석 기록 생성, 중복 주문 생성 방지
- 여러 row나 여러 테이블을 하나의 논리 작업으로 묶어야 할 때: 쿠폰 발급, 이벤트 참여 처리
- 여러 서버 중 하나만 실행해야 할 때: 배치, 캐시 갱신, 통계 계산
- 외부 시스템 호출이 중복되면 안 될 때: 결제 승인, 포인트 적립, 알림 발송
- Redis 같은 별도 분산 락 인프라 없이 DB만으로 간단히 동시 실행을 제어하고 싶을 때

<details>
<summary>여러 row나 여러 테이블을 하나의 논리 작업으로 묶는 경우</summary>

쿠폰 발급을 예로 들면 실제로는 여러 일이 함께 일어날 수 있다.

```text
1. 이 사용자가 이미 쿠폰을 받았는지 확인
2. 쿠폰 재고 확인
3. 쿠폰 발급 이력 저장
4. 쿠폰 재고 감소
5. 이벤트 참여 이력 저장
```

이 경우 `coupon` row만 잠그면 발급 이력 중복을 완전히 설명하기 어렵고, 발급 이력 row는 아직 존재하지 않을 수도 있다. 또 이벤트 참여 이력까지 함께 처리한다면 여러 테이블이 하나의 작업으로 묶인다.

이때 네임드 락을 사용하면 특정 row 하나가 아니라 `1번 사용자에게 100번 쿠폰을 발급하는 작업` 자체에 입구를 하나만 만들 수 있다.

```sql
SELECT GET_LOCK('issue-coupon:user:1:coupon:100', 3);
```

즉 네임드 락은 데이터 하나를 잠그기보다, 여러 쿼리로 구성된 하나의 비즈니스 작업이 동시에 실행되지 않도록 막는 데 사용할 수 있다.

</details>

<details>
<summary>여러 서버 중 하나만 실행해야 하는 경우</summary>

애플리케이션 서버가 여러 대라면 서비스 코드의 메모리 락은 서버 간에 공유되지 않는다.

```text
서버 A: daily-statistics 배치 실행
서버 B: daily-statistics 배치 실행
```

각 서버가 자기 메모리에서만 락을 잡으면 두 서버가 동시에 배치를 실행할 수 있다.

반면 네임드 락은 MySQL 서버가 중앙에서 관리한다.

```sql
SELECT GET_LOCK('batch:daily-statistics', 0);
```

여러 서버가 같은 MySQL에 같은 이름의 락을 요청하면 하나만 락 획득에 성공한다. 그래서 락을 잡은 서버만 배치를 실행하고, 나머지 서버는 실행을 건너뛰게 만들 수 있다.

</details>

<details>
<summary>외부 시스템 호출이 중복되면 안 되는 경우</summary>

결제 승인 같은 작업은 DB row lock만으로 부족할 수 있다.

```text
1. 주문 상태 확인
2. PG사 결제 승인 API 호출
3. 결제 결과 DB 저장
```

문제는 외부 API 호출은 DB 트랜잭션처럼 롤백할 수 없다는 점이다. 동시에 두 요청이 들어오면 둘 다 PG사에 승인 요청을 보낼 수 있다.

이때 같은 주문에 대한 결제 승인 로직 앞에 네임드 락을 둘 수 있다.

```sql
SELECT GET_LOCK('payment:approve:order:123', 5);
```

이렇게 하면 같은 주문의 결제 승인 작업은 한 번에 하나만 실행된다. 다만 결제 같은 중요한 작업은 네임드 락만 믿기보다 주문 상태 조건, 결제 이력의 `UNIQUE` 제약, 외부 API의 idempotency key 같은 방어도 함께 두는 것이 좋다.

</details>

<details>
<summary>Redis 없이 DB로 간단히 분산 락을 쓰는 경우</summary>

여러 서버 사이에서 하나의 작업만 실행하게 하려면 서버들이 함께 확인할 수 있는 중앙 기준이 필요하다.

```text
서버 A
서버 B
서버 C
```

이 서버들이 모두 같은 MySQL을 사용하고 있다면, MySQL 네임드 락을 간단한 분산 락처럼 사용할 수 있다.

Redis, ZooKeeper 같은 별도 락 인프라를 두기 부담스럽고, 작업의 규모나 빈도가 크지 않다면 DB만으로 동시 실행을 제어하는 선택지가 될 수 있다.

다만 네임드 락은 DB 커넥션에 묶이는 락이므로 락 해제, 타임아웃, 커넥션 풀 사용에 주의해야 한다.

</details>

정리하면 서비스 단의 메모리 락은 단일 서버 안에서는 효과가 있지만, 여러 서버 사이에서는 공유되지 않는다. 네임드 락은 MySQL 서버가 중앙에서 관리하므로 여러 서버가 같은 DB를 기준으로 작업 단위의 동시 실행을 제어할 수 있다.

다만 네임드 락만으로 데이터 정합성을 보장하려고 하면 위험하다. 같은 작업인데 다른 락 이름을 사용하거나, 아예 네임드 락을 거치지 않고 데이터를 변경하는 코드가 있으면 우회될 수 있기 때문이다.

실무에서는 보통 DB가 직접 보장해야 하는 규칙과 네임드 락의 역할을 구분해서 사용한다.

- 절대 깨지면 안 되는 규칙은 `UNIQUE`, `FOREIGN KEY` 같은 DB 제약조건으로 보장한다.
- 특정 row의 상태 변경이나 수량 차감은 조건부 `UPDATE`나 레코드 락으로 보호한다.
- 여러 서버에서 하나의 비즈니스 작업이 동시에 실행되지 않게 하고 싶을 때 네임드 락을 보조 수단으로 사용한다.

MySQL 8.0부터는 여러 개의 네임드 락을 동시에 사용할 수 있으며, `RELEASE_ALL_LOCKS()` 함수로 현재 세션이 획득한 모든 네임드 락을 한 번에 해제할 수 있다.

```sql
SELECT RELEASE_ALL_LOCKS();
```

### 5.2.4 메타데이터 락

메타데이터 락(Metadata Lock)은 데이터베이스 객체(테이블, 뷰 등)의 이름이나 구조를 변경할 때 자동으로 획득되는 잠금이다.

사용자가 직접 획득하거나 해제하는 것이 아니라 `ALTER TABLE`, `DROP TABLE`, `RENAME TABLE` 등의 DDL을 실행하면 자동으로 설정된다.

예를 들어 어떤 세션에서 테이블의 구조를 변경하는 동안 다른 세션이 같은 테이블을 동시에 사용하면 문제가 생길 수 있다. 한쪽에서는 예전 구조를 기준으로 데이터를 읽고 있는데, 다른 쪽에서는 컬럼을 추가하거나 테이블 이름을 바꿔버릴 수 있기 때문이다.

그래서 MySQL은 테이블의 이름이나 구조가 변경되는 동안 메타데이터 락을 이용해 충돌이 생길 수 있는 작업을 대기시킨다.

`RENAME TABLE`은 여러 개의 테이블 이름을 하나의 명령으로 동시에 변경할 수 있으며, 이를 통해 서비스 중간에 테이블이 존재하지 않는 상태를 방지할 수 있다.

```sql
RENAME TABLE
    rank TO rank_backup,
    rank_new TO rank;
```

반대로 아래와 같이 두 개의 명령으로 나누어 실행하면 두 명령 사이에 `rank` 테이블이 존재하지 않는 순간이 발생할 수 있다.

```sql
RENAME TABLE rank TO rank_backup;
RENAME TABLE rank_new TO rank;
```

#### 대용량 테이블 교체 전략

대용량 테이블의 구조를 변경해야 하는 경우에는 서비스 중단 시간을 최소화하기 위해 다음과 같은 방법을 사용할 수 있다.

여기서 서비스 중단 시간을 줄인다는 말은 전체 작업 시간이 반드시 짧아진다는 의미가 아니다. 기존 서비스 테이블이 잠기거나 대기하는 시간을 줄인다는 의미에 가깝다.

대용량 테이블에 `ALTER TABLE`을 직접 실행하면 테이블의 구조가 바뀌면서 데이터나 인덱스를 새 구조에 맞게 다시 정리해야 할 수 있다.

예를 들어 컬럼을 추가하거나, 컬럼 타입을 변경하거나, 인덱스를 추가하는 작업은 단순히 이름만 바꾸는 작업이 아니다. MySQL은 변경 내용에 따라 기존 데이터를 새 구조에 맞게 재구성하거나 인덱스를 다시 만들어야 할 수 있고, 테이블이 클수록 이 작업은 오래 걸릴 수 있다.

이때 직접 `ALTER TABLE rank ...`를 실행하면 구조 변경이 진행되는 동안 메타데이터 락 때문에 다른 쿼리가 대기하거나 쓰기 작업이 제한될 수 있다.

반면 새 구조의 테이블을 미리 만들어 데이터를 복사한 뒤 마지막에 `RENAME TABLE`로 이름만 교체하면, 오래 걸리는 데이터 복사 작업은 기존 테이블을 계속 사용하면서 뒤에서 수행할 수 있다.

`RENAME TABLE`은 이미 준비된 테이블의 이름이라는 메타데이터만 변경하는 작업이므로 보통 짧게 끝난다. 즉 전체 작업 시간이 줄어드는 것이 아니라, 서비스가 멈추거나 대기하는 시간이 마지막 교체 순간으로 줄어드는 것이다.

1. 새로운 테이블을 생성한다.
2. 기존 데이터를 여러 스레드로 나누어 미리 복사한다.
3. 마지막 변경된 데이터만 짧게 복사한다.
4. `RENAME TABLE`로 새로운 테이블과 기존 테이블의 이름을 교체한다.
5. 기존 테이블을 삭제한다.

이 방법은 대부분의 데이터를 미리 복사해 두고 마지막에 잠깐만 테이블을 잠그기 때문에 서비스 중단 시간을 최소화할 수 있다.

### 백업 락 (Backup Lock)

MySQL 8.0부터는 온라인 백업을 위해 백업 락이 추가되었다.

기존의 글로벌 락은 모든 변경 작업을 막았지만, 백업 락은 DDL만 차단하고 일반적인 DML은 허용한다.

백업 락의 목적은 서비스를 계속 처리하면서도 백업 결과가 깨지지 않도록 하는 것이다.

백업 중에도 `INSERT`, `UPDATE`, `DELETE` 같은 일반적인 데이터 변경은 허용된다. InnoDB는 트랜잭션과 로그를 이용해 특정 시점의 일관된 상태를 복구할 수 있기 때문이다.

하지만 `ALTER TABLE`, `DROP TABLE`, `RENAME TABLE` 같은 DDL은 테이블의 구조나 이름 자체를 변경한다. 백업 도중에 테이블 구조가 바뀌면 데이터 파일은 예전 구조인데 메타데이터는 새 구조가 되는 식으로 백업 결과가 애매해질 수 있다.

그래서 백업 락은 데이터 변경은 허용하지만, 백업 대상의 구조와 메타데이터를 바꾸는 작업은 막는다.

```sql
LOCK INSTANCE FOR BACKUP;

-- 백업 수행

UNLOCK INSTANCE;
```

백업 락을 획득하면 다음 작업은 수행할 수 없다.

- 데이터베이스 및 테이블 생성, 수정, 삭제
- 사용자 생성 및 비밀번호 변경
- REPAIR TABLE
- OPTIMIZE TABLE

반면 다음 작업은 정상적으로 수행된다.

- SELECT
- INSERT
- UPDATE
- DELETE

따라서 서비스 운영 중에도 데이터 변경을 허용하면서 안정적으로 백업을 수행할 수 있다.

---

### 글로벌 락과 백업 락 비교

| 구분 | 글로벌 락 | 백업 락 |
|------|----------|----------|
| 범위 | MySQL 서버 전체 | DDL 중심 |
| SELECT | 가능 | 가능 |
| INSERT / UPDATE / DELETE | 불가능 | 가능 |
| DDL | 불가능 | 불가능 |
| 사용 목적 | 전체 백업 | 온라인 백업 |
| 서비스 영향 | 매우 큼 | 상대적으로 적음 |

## 5.3 실습 문제

### 5.3.1 같은 이름의 네임드 락 대기 확인

네임드 락이 문자열 이름을 기준으로 동작한다는 것을 확인하는 실습이다.

세션 A에서 다음 쿼리를 실행한다.

```sql
SELECT GET_LOCK('test-lock', 10);
```

세션 B에서 같은 이름의 락을 요청한다.

```sql
SELECT GET_LOCK('test-lock', 3);
```

세션 A가 락을 해제하지 않으면 세션 B는 3초 동안 기다리다가 락 획득에 실패한다.

세션 A에서 락을 해제한다.

```sql
SELECT RELEASE_LOCK('test-lock');
```

확인할 점은 다음과 같다.

- 같은 문자열 이름의 네임드 락은 동시에 하나의 세션만 획득할 수 있다.
- 다른 문자열 이름을 사용하면 서로 다른 락으로 판단한다.

---

### 5.3.2 네임드 락이 row를 직접 막지 않는 것 확인

네임드 락이 실제 테이블 row를 잠그는 락이 아니라는 것을 확인하는 실습이다.

먼저 테스트용 테이블을 준비한다.

```sql
CREATE TABLE coupon (
    id BIGINT PRIMARY KEY,
    quantity INT NOT NULL
);

INSERT INTO coupon(id, quantity)
VALUES (1, 10);
```

세션 A에서 네임드 락을 획득한다.

```sql
SELECT GET_LOCK('coupon:1', 10);
```

세션 B에서 같은 `coupon.id = 1` row를 수정한다.

```sql
UPDATE coupon
SET quantity = quantity - 1
WHERE id = 1;
```

이 `UPDATE`는 네임드 락 때문에 막히지 않는다.

확인할 점은 다음과 같다.

- `GET_LOCK('coupon:1', 10)`은 `coupon` 테이블의 `id = 1` row를 잠그지 않는다.
- 네임드 락은 같은 이름으로 `GET_LOCK()`을 호출하는 작업끼리만 대기시킨다.
- 특정 row 변경을 막고 싶다면 레코드 락이나 조건부 `UPDATE` 같은 방식을 사용해야 한다.

실습이 끝나면 락을 해제한다.

```sql
SELECT RELEASE_LOCK('coupon:1');
```

---

### 5.3.3 작업 단위로 하나만 실행되는 것 확인

네임드 락을 작업의 입구처럼 사용할 수 있다는 것을 확인하는 실습이다.

세션 A에서 배치 작업을 실행한다고 가정하고 다음 쿼리를 실행한다.

```sql
SELECT GET_LOCK('batch:daily-statistics', 0);
```

결과가 `1`이면 락을 획득한 것이므로 배치를 실행한다고 생각한다.

세션 B에서 같은 쿼리를 실행한다.

```sql
SELECT GET_LOCK('batch:daily-statistics', 0);
```

세션 A가 아직 락을 가지고 있다면 세션 B의 결과는 `0`이 된다. 이 경우 이미 다른 서버나 프로세스가 작업을 실행 중이라고 보고 이번 실행을 건너뛰면 된다.

확인할 점은 다음과 같다.

- 네임드 락은 여러 서버나 여러 프로세스에서 하나의 작업만 실행되도록 만들 수 있다.
- 이때 락 이름은 `batch:daily-statistics`처럼 작업의 의미를 표현하는 문자열 컨벤션이다.

실습이 끝나면 락을 해제한다.

```sql
SELECT RELEASE_LOCK('batch:daily-statistics');
```

### 5.3.4 RENAME TABLE 교체 전략 확인

대용량 테이블 구조 변경 전략에서 `ALTER TABLE`과 `RENAME TABLE`의 성격 차이를 확인하는 실습이다.

먼저 기존 테이블을 만든다.

```sql
CREATE TABLE rank (
    id BIGINT PRIMARY KEY,
    score INT NOT NULL
);

INSERT INTO rank(id, score)
VALUES
    (1, 100),
    (2, 90);
```

새 구조의 테이블을 따로 만든다.

```sql
CREATE TABLE rank_new (
    id BIGINT PRIMARY KEY,
    score INT NOT NULL,
    score_type VARCHAR(20) NOT NULL
);
```

기존 데이터를 새 구조에 맞게 복사한다.

```sql
INSERT INTO rank_new(id, score, score_type)
SELECT id, score, 'DEFAULT'
FROM rank;
```

마지막에 테이블 이름을 한 번에 교체한다.

```sql
RENAME TABLE
    rank TO rank_backup,
    rank_new TO rank;
```

확인할 점은 다음과 같다.

- `ALTER TABLE`은 기존 테이블의 구조를 직접 변경한다.
- `RENAME TABLE`은 이미 준비된 테이블의 이름이라는 메타데이터를 교체한다.
- 이 전략은 전체 작업 시간을 줄이는 것이 아니라, 기존 서비스 테이블이 영향을 받는 시간을 줄이는 방식이다.
